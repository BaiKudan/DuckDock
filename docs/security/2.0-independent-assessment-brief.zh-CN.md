# DuckDock 2.0 独立安全评估委托书

## 独立性与交付目标

评估方不得是 DuckDock 2.0 的实现者或最终签字人。测试对象必须是候选生产
commit、backend/frontend 镜像 SHA-256 以及 production-like HA 目标环境。
报告需列明测试人员、日期、方法、限制、发现、风险分级、复现证据和复测结论。
正式授权要求 Critical/High 未关闭项均为零；风险接受不能把未关闭项伪装成已修复。

## 必测范围

- 本地账号、OIDC/LDAP/SCIM、JWT、Reporter/Worker/Workload credential 的签发、
  越权、撤销、重放、租户隔离和四眼审批；
- `/api/v1` 与冻结 `/api/v2` 的对象级/功能级授权、批量赋值、速率限制、
  错误信息、上传状态机、幂等键冲突和 TOCTOU；
- Package/Handover 的 Ed25519 签名、SBOM/digest 绑定、密钥轮换、回滚回执、
  对象下载 URL 和不可变证据；
- SSRF、DNS rebinding、重定向、TLS SNI/证书校验、Webhook、SSO 和外部 LLM/
  Langfuse/Hermes/OTLP 端点；
- ZIP bomb、路径穿越、Git 路径、恶意 Skill/Agent 包、内容类型、超限对象和
  解析器差异；
- Agent 特有风险：Prompt injection 不能变成平台工具越权，Observation IO、
  annotation、embedding、secret 不得进入 Audit/Outbox/日志/工单，LLM 建议
  不得绕过确定性发布策略和人工审批；
- Kubernetes/Compose 的 TLS、Secrets、容器权限、网络、egress、数据存储、
  备份、监控入口、镜像 provenance/SBOM 与供应链；
- 多租户并发、失败重试、Outbox/lease replay、节点/zone 故障期间的安全退化。

## 测试安全边界

只允许从机器可验证委托中列明的来源 CIDR/测试机，使用列明的测试账号，在最长
30 天授权窗口内测试精确 target/release。禁止 DoS、破坏性改数、生产数据外传、
持久化/后门、社工、物理测试以及接触未授权第三方系统；容量测试属于独立 GA phase，
不在本委托内。Security 与 Operations 都有立即停止权，评估方须在 15 分钟内确认。
为评估方创建最小权限、可撤销、有期限的测试身份，结束后由 Operations 证明全部撤销
并轮换接触过的 secret。证据必须静态加密、不得记录 secret 或保留生产数据，窗口后
最多 90 天内删除并交付删除证明。

## 必交证据

1. 报告 PDF 与 SHA-256；
2. 精确 source commit、backend/frontend image digest、API contract digest；
3. 工具及规则版本、人工测试说明、覆盖与未覆盖范围；
4. 每项发现的复现、修复 commit、复测状态；
5. `open_critical=0`、`open_high=0` 的最终签字页；
6. 用于 GA 授权 JSON 的 provider、完成时间和报告 digest；
7. 证据删除证明。

execution campaign 创建并审阅后、测试开始前，项目 Security 角色必须先按
`ops/ga/security-assessment-engagement.example.json` 固化 provider/assessor、最终
release/target、窗口、来源、测试账号、禁止动作、急停、数据处置和交付物。委托由
approval policy 中精确授权的 Security identity 签署；授权时间不得早于 campaign 创建，
测试窗口必须完全落在 campaign 窗口内，邮件或口头 scope 不能替代：

```bash
ssh-keygen -Y sign \
  -n duckdock-security-assessment-engagement \
  -f /secure/security-role-signing-key \
  /secure/duckdock-2.0-security-engagement.json
```

评估方还需交付一份严格符合
`ops/ga/security-assessment-report.example.json` 的机器可读原始报告。它必须逐条列出
finding ID、severity、open/closed、受影响组件、发现时间和复测时间，并给出按五档
严重度统计的 open/closed 数；不能只提供 `open_high=0` 汇总。该 JSON 同时绑定
target ID、API contract digest、source commit、两个不可变镜像摘要以及最终 PDF 的
路径和 SHA-256。五类 scope 不得删减，methodologies 至少包含
`penetration-test` 与 `manual-code-review`。项目方不得代替评估方生成或签署这份原始
报告。

组织发布机构必须先在 `duckdock-ga-approval-policy-v2` 的
`independent_security_assessors` 中将评估机构名称映射到评估方精确 identity，并把
该 identity 的公钥加入与四方审批共享的 allowed-signers。签署委托的 Security identity
也必须是 policy 中 Security 角色的精确成员。评估方 identity、公钥与
任何 Product/Architecture/Security/Operations 审批人都不得复用；证据文件不能自行
指定另一份信任库。

评估方使用自己的 OpenSSH key 对 v2 机器可读原始报告签名。报告必须引用 Security
签署委托的 engagement ID 与 SHA-256，且开始/结束时间均在授权窗口内。报告中的
`execution_identity` 必须逐项等于批准的 CIDR/测试机/账号，
`data_handling_attestation` 必须确认工作证据加密、未记录 secret、未保留生产数据并已
在截止日前删除。由于 JSON 已内容寻址绑定委托和最终 PDF，修改三者任一文件都会被
最终门禁拒绝：

```bash
ssh-keygen -Y sign \
  -n duckdock-security-assessment \
  -f /secure/assessor-signing-key \
  /secure/duckdock-2.0-final-assessment.json
```

发布负责人运行采集器生成 v3 GA wrapper；采集器不接收临时 allowed-signers 路径，
只使用显式传入的组织发布策略：

```bash
python backend/scripts/collect_ga_independent_security.py \
  --target-environment customer-production \
  --source-commit "$DUCKDOCK_GA_SOURCE_COMMIT" \
  --backend-image "$DUCKDOCK_GA_BACKEND_IMAGE" \
  --frontend-image "$DUCKDOCK_GA_FRONTEND_IMAGE" \
  --contract-digest "$DUCKDOCK_GA_CONTRACT_DIGEST" \
  --provider "Independent Security Lab" \
  --security-authorizer-identity security@duckdock.example \
  --assessor-signer-identity assessor@independent-security.example \
  --assessment-engagement /secure/duckdock-2.0-security-engagement.json \
  --engagement-signature /secure/duckdock-2.0-security-engagement.json.sig \
  --assessment-report /secure/duckdock-2.0-final-assessment.json \
  --assessment-signature /secure/duckdock-2.0-final-assessment.json.sig \
  --approval-policy /release-authority/duckdock-ga-approval-policy.json \
  --output /secure/evidence/independent-security.json
```

采集器和最终生产授权器都会先用 Security role 重验委托签名/安全边界，再用 assessor
role 重验报告签名，重算 engagement/PDF digest、逐条重算 finding 统计、确认
Critical/High 为零并核对所有投影。自选信任根、越过窗口、放宽禁止动作、替换委托、
修改 wrapper 摘要、隐藏 finding、伪造 `signature_verified`、签名后修改 PDF 或由内部
审批人代签报告都不能通过。

项目方可以提前提供架构图、OpenAPI snapshot、测试账号矩阵、数据分类、
`docs/operations-runbook.zh-CN.md`、本委托书以及 RC 证据。项目自己的 pytest、
dependency audit、镜像扫描和自测可作为输入，但不得被标记为“独立评估”。
